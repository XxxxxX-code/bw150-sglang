## 第 2 段 · 基线对比

### 2.1 为什么不能直接用出厂默认：出厂默认在本机必然崩溃

规则要求基线用「官方镜像 + 推理框架出厂参数」。我们照此执行，**出厂默认在本机启动即崩溃**，
已完整留存原始日志（`submit/logs/00_default_crash.log`）。崩溃链条已定位到源码行：

1. `server_args.py:1264-1267` —— `mamba_scheduler_strategy` 默认 `auto` → 解析为 `no_buffer`
2. `server_args.py:2651-2658` —— `no_buffer` + radix cache 时，框架把 `page_size` **强制改回 1**
3. `mem_cache/mamba_radix_cache.py:434-438` —— `MambaRadixCache v1` 硬 assert `page_size == 1`（因此第 2 步是必须的）
4. 但 DCU 的 fa3 attention kernel **硬要求 `page_size == 64`**

日志原文（两句关键行）：

```
Qwen3_5ForConditionalGeneration with radix cache requires page_size=1 in the current
Mamba scheduling mode (no_buffer), but got 64. Automatically setting page_size=1.
RuntimeError: Paged KV cache block size must be 64
```

即：**出厂默认的两个子系统在本机互斥**，不存在「纯出厂默认且能跑起来」的配置。

### 2.2 最小必要偏差基线的两条候选，取更快者

只做能解开上述死锁的最小改动，其余一切保持出厂默认（不设 `--mem-fraction-static`、
不设 `--context-length`、不设 `--max-running-requests`、不加任何性能 env、不用投机解码）：

| 候选 | 改动 | 保住的东西 | 生效并发（实测） |
|---|---|---|---|
| **B1** | 默认 + `--mamba-scheduler-strategy extra_buffer --page-size 64` | 出厂默认的 radix cache | 24（`ratio = 3+2 = 5`，池 90/5） |
| **B2**（采纳） | 默认 + `--disable-radix-cache --page-size 64` | 出厂默认的 `no_buffer` 策略 | **121**（`ratio = 1`） |

> 注：`extra_buffer` + `--disable-radix-cache` 组合会直接 ValueError（`server_args.py:2622-2631`），
> 两条候选必须各自配对自己的策略，不能只加 flag。
> 取更快者作正式基线是对我们自己更不利、也更安全的选择（规则禁止的是「调低基线」）。

B2 实测生效值（启动日志 `submit/logs/05_server_b2.log`）：
`max_running_requests=121, max_total_num_tokens=320192, context_len=262144, mem_fraction_static=0.7333`（框架自动算得）。

两条候选都实测了，**B2 在每一个档位都更快**，故采纳 B2：

| 档位 | B1（保留 radix cache） | B2（保留 no_buffer 策略） | 胜者 |
|---|---|---|---|
| 生效并发 | 24 | **121** | B2 |
| ShareGPT conc 1 | 27.07 | **26.92** | 持平 |
| ShareGPT conc 16 | 286.07 | **322.89**（+12.9%） | **B2** |
| ShareGPT conc 64 | 302.49 | **556.09**（+83.8%） | **B2** |

值得注意的是 conc 16 这一档：B1 的 24 并发帽并未被触及（16 < 24），
B2 仍然快 12.9% —— 说明 `no_buffer` 策略本身的每步开销就比 `extra_buffer` 低，
而不只是「并发更高」这一个原因。所以在两条候选之间取 B2 是有机理支撑的，不是碰运气。

> **口径说明（如实标注）**：B2 一列用的是第 4 段 tag `b2r3` 的 **3 轮中位数**
> （26.92 / 322.89 / 556.09），与正式成绩同源、可直接核对原始日志。
> **B1 一列是早期单轮筛选的读数，其原始日志未随本次重跑一并归档**
> （见文末「日志归档范围声明」），仅作为「两条候选之间如何取舍」的判据保留，
> 不作为任何成绩数字。报告中的「提升率」一律以第 4 段的 3 轮中位数为分母。

### 2.3 提升率

分母 = **本机 B2 自测基线**（3 轮中位数）。汇总如下，逐档明细与方差见第 4 段。

| 指标 | 基线 B2 | 本方案 | 提升率 |
|---|---|---|---|
| ShareGPT 输出吞吐 conc 1 | 26.92 tok/s | 67.96 tok/s | **+152.5%** |
| ShareGPT conc 4 | 117.27 | 220.50 | **+88.0%** |
| ShareGPT conc 16 | 322.89 | 486.90 | **+50.8%** |
| ShareGPT conc 32 | 450.78 | 647.74 | **+43.7%** |
| ShareGPT conc 64 | 556.09 | 801.83 | **+44.2%** |
| SLA 4K/1K 最大并发 | 16 | **32** | **+100%** |
| SLA 64K/1K 最大并发 | 3 | **6** | **+100%** |

> **提升率随并发升高而收敛（+152% → +44%）是必然的**：低并发档的瓶颈是**单流解码速度**
> （EAGLE 直接受益），高并发档的瓶颈转向**显存带宽与调度**，投机解码的边际收益被摊薄。
> 这条曲线本身也说明我们没有在某一档上做特化 —— 全档位同向、无退化档。

### 2.4 横向参考：官方 BW100 基线（**不作为分母**）

官方 BW100 ShareGPT 基线：conc 1/4/16/32/64 = 21.454 / 106.207 / 307.45 / 435.996 / 528.158 tok/s。

一个重要的反推结论：我们**去掉投机解码**、其余配置相近地跑 BW150（配置 A），得到
26.88 / 117.38 / 323.44 / 450.28 / 555.54 tok/s —— 相对官方 BW100 只有 +3% ~ +25%，
与两卡的硬件差异量级相当。这说明**官方 BW100 基线没有启用投机解码**，
而这也正是我们提升率的主要来源之一（见第 3 段 3.2）。

## 第 3 段 · 优化方法（权重最高）

起点：第三方提供的参考启动脚本（下称「参考配置」）。它的单流很快
（conc 1 输出吞吐 66.54 tok/s，TPOT 中位 14.55 ms），但**高并发档塌陷**：
生效并发只有 18，conc 64 时 TTFT 高达 22,276 ms。

下面 5 条按**收益排序**：3.1 解开并发上限 > 3.2 保住投机解码 > 3.4 prefill 批处理 >
3.3 上下文修复 > 3.5 内核包。其中 3.3 与 3.5 的价值不在吞吐，而分别是
「让 64K 场景从 0 分变成有分」和「一条只值 3% 但顺手可得的增益」。
每一步都给出**实测数字**，被推翻的判断也如实记录（3.5）。

### 3.1 解开并发上限：18 → 64（最大单项收益）

**机理链条**（每一环都定位到源码行，不是推测）：

```
--speculative-algorithm EAGLE
  → server_args.py:4035-4039 强制 max_running_requests = 48
  → model_runner_kv_cache_mixin.py:919-921   max_num_reqs = min(48, 2048) = 48
  → model_runner_kv_cache_mixin.py:925-929   max_num_reqs = min(48, max_mamba_cache_size // ratio)
                                              = min(48, 90 // 5) = 18
  → ratio = 3(基础) + 2(extra_buffer 且 overlap 开启) = 5
             （同文件 66-69、_calculate_mamba_ratio() 280-292）
```

所以并发被三重夹住：EAGLE 强制的 48 帽、`extra_buffer` 的 ratio=5、以及
`max_mamba_cache_size=90` 的池大小。三处同时松开：

| 改动 | 机理 | 效果 |
|---|---|---|
| `--mamba-scheduler-strategy no_buffer` + `--disable-radix-cache` | `disable_radix_cache` 时 `ratio` 直接塌回 **1**，且 `max_mamba_cache_size` 直接等于 `max_running_requests`（`kv_cache_mixin.py:194-205`）。**必须成对使用**，因为 `extra_buffer + disable_radix_cache` 会 ValueError（`server_args.py:2622-2631`，框架自己的报错信息就给出了正确配对） | 池大小不再需要 ×5 冗余 |
| `--max-running-requests 64` | 顶掉 EAGLE 强制的 48 帽；同时消掉一笔**过量预留**：`kv_cache_mixin.py:178-191` 按 `server_args.max_running_requests × speculative_num_draft_tokens`（= 48×4）预扣投机中间态，而实际缓冲形状只有 `max_num_reqs+1`（`memory_pool.py:299-321`） | 省 GB 级显存 + 解开 48 帽 |
| `--mamba-ssm-dtype bfloat16` | `ssm_state` 出厂是 **fp32**，每槽 70.9 MB。降为 bf16 后每槽 35.8 MB | 实测 64 槽下 `ssm_state` 6.40 GB → **2.29 GB** |

**实测效果**：生效并发 18 → **64**；conc 64 的 TTFT 从参考配置的 22,276 ms →
**398.8 ms（−98.2%）**；conc 64 输出吞吐 66.54 → 746.30 tok/s。

**为什么这条最值钱**：官方 SLA（4.1.3）与吞吐曲线都由「同时在飞的请求数」决定。
18 槽的服务在物理上到不了官方基线在 conc 64 达到的 528 tok/s —— 分母是我方基线，
但这条改动同时也是**相对官方基线**唯一能追平高并发档的前提。

代价：`--disable-radix-cache` 丢掉了前缀缓存，高并发下重复 prompt 需要重复 prefill。
取舍在第 5 段说明。

### 3.2 保住 EAGLE 投机解码（提升率的主要来源）

参考配置已经用了 `--speculative-algorithm EAGLE`（走模型内置 MTP 头
`qwen3_5_mtp.py`，`--speculative-num-steps 3 --speculative-eagle-topk 1
--speculative-num-draft-tokens 4`）。**我们保留它**，理由是：

- 实测 accept len 2.27 ~ 2.58、accept rate 0.42 ~ 0.68，即每次前向产出约 2.4–2.6 个 token；
- 第 2.4 节的反推表明**官方基线没有投机解码**，因此这是我们与官方基线拉开差距的主要机制；
- 3.1 的改动已经解开了并发帽，EAGLE 不再需要为并发让路。

### 3.3 上下文长度修复：打开 64K/1K 场景的门

参考配置与我们的 c2 都带 `--context-length 65535`。官方 SLA 的 64K/1K 场景需要
65536 + 1024 = 66560 token，**超过 65535 会被直接拒绝**，该场景一分都拿不到。

修复：把 `--context-length` 调回**出厂默认 262144**。这**不花费任何显存**——
KV 池是按显存算的（实测 518,784 token），本来就远超 65,535。

> 注：`SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1` 在这里**救不了**
> （`model_config.py:604-632`：它只在「配置值 > 模型推导上限」时放开，
> 而 65535 < 66560 属于「配置值反而更小」，不触发）。

### 3.4 放大 prefill 批处理（SLA 两条指标的关键杠杆）

**问题定位**：C3 实测的 SLA 各档 TTFT 显示，TTFT 随并发近似线性增长
（4K 场景 conc1 394ms → conc4 964ms → conc8 1629ms）。这个斜率来自出厂默认的
`chunked_prefill_size = 8192`：**4K 输入下每个 prefill chunk 只装得下 2 条请求**，
8 并发就要排 4 个 chunk。64K 场景同理，一条 64K 请求要被切成 8 段。

**改动**：`--chunked-prefill-size 32768 --max-prefill-tokens 32768`，同时把
`--mem-fraction-static` 从 0.90 降到 0.85。

**为什么必须同时降 mem-fraction**：chunk 激活显存 ∝ chunk size。C3 起服后
`available_gpu_mem` 只剩 2.64 GB，而 KV 池（518,784 token）远超实际需求
（实测只有 64 并发 × 平均约 600 token）。降 mem-fraction 把这笔冗余换成激活余量，
`available_gpu_mem` 2.64 → **5.82 GB**，KV 池仍有 421,376 token（足够 64 并发）。

**实测效果**（相对 C3；C4 = 最终配置，仅差内核包一项，见 3.5）：

| 指标 | C3 | C4 | 变化 |
|---|---|---|---|
| 4K SLA conc 8 的 TTFT | 1629.26 ms | **779.11 ms** | **2.09×** |
| 4K SLA conc 32 的 TPOT | 42.85 ms | **39.79 ms** | −7% |
| 64K SLA conc 1 的 TTFT | 11287.6 ms | **6656.24 ms** | **1.70×** |
| 64K SLA 最大并发 | 1 | **2** | 翻倍 |
| ShareGPT conc 32 / 64 | 645.56 / 768.63 | 648.92 / **782.71** | +0.5% / +1.8% |

即：这条改动**没有牺牲 ShareGPT 吞吐**（甚至略升），却把两条 SLA 指标的余量显著拉开。
64K 档的瓶颈是「8 段串行 prefill」，改成 2 段后 TTFT 直接砍掉 41%。

> ⚠️ **读这张表时注意分阶段**：这里的「64K SLA 最大并发 1 → 2」是 **C3 → C4 这一步**
> 的增益（当时只探到 conc 2）。最终配置在把并发档探到 6 之后，
> 64K 的最大并发是 **6**，相对基线的完整对比见第 4.3 节 —— 不要把它和这里的 2 混起来看。

### 3.5 内核包消融：一次被自己的复核推翻的结论（诚实记录）

计划里最被看好的一条是「算子/内核替换」—— 官方 HCU cookbook 的 `QWEN3_COOKBOOK_ENV`
（`SGLANG_USE_AITER_LINEAR_ATTN` / `SGLANG_USE_CAUSAL_CONV1D` / `SGLANG_USE_AITER_AR`
等）。本模型 64 层里 48 层是 GDN 线性注意力，先验判断是「最大的单点机会」。
验证过程本身还顺带排除了两个直接崩溃的 env（见 3.7）。

**做法**：把内核包全开（配置 C4），再用**除整包 env 外一切相同**的配置（C6）做消融。

#### 干净的证据（同 prompt 数 n=300，同一 seed，唯一变量是 env 包）

| 指标 | 有内核包（C4） | 无内核包（C6） | 结论 |
|---|---|---|---|
| ShareGPT conc 32 | 648.92 | 631.12 | 有内核包 **+2.8%** |
| ShareGPT conc 64 | 782.71 | 756.05 | 有内核包 **+3.5%** |
| 4K SLA 最大并发 | 32 | 32 | 持平 |

#### 被推翻的「证据」（记录一次自我纠错）

第一版消融时我得到过一张看起来很有说服力的表，结论是「内核包在长序列 prefill 上
倒退 1.5–1.6×，把 64K SLA 从 4 砍到 2，因此不采纳」。复核时发现**这张表不可比**：

| 被误用的对比 | 有内核包（C4） | 无内核包（C6） |
|---|---|---|
| 64K SLA conc 1 TTFT | 6656 ms | 4131 ms |
| 探测口径 | `--num-prompts 3`，有 warmup | `--num-prompts 4`，`--warmup 0` |
| — | — | — |
| **换成同口径（n=4、warmup 0）后重测** | | |
| 64K SLA conc 1 TTFT | 见 §4.3（本轮补测） | 4131 ms |
| **B2 基线**（本身不带任何内核包）同口径 | **4121.5 ms** | — |

关键的反证是最后一行：**B2 基线**（出厂默认 + 最小必要偏差，**完全没有**内核包）
在 n=4、warmup 0 的口径下，64K conc1 的 TTFT 是 **4121.5 ms** —— 和无内核包的 C6
（4131.0 ms）几乎逐位相同，而远离那个 n=3 口径下的 6262 ms 读数。

**这个 1.5× 的摆动完全来自统计量本身，与配置无关。** 四个日志的原始读数
（均为 `--warmup 0`、同一 seed、同一 65536/1024 输入输出长度）：

| 配置 | n | Median TTFT | Mean TTFT | P99 TTFT | 总时长 |
|---|---|---|---|---|---|
| B2 基线 | 3 | 6262.23 | 7666.73 | 14578.48 | 86.74 s |
| B2 基线 | 4 | **4121.50** | 5938.08 | 14370.01 | 136.60 s |
| C4（带内核包） | 3 | 6656.24 | 8012.33 | 15116.05 | 42.15 s |
| C6（无内核包） | 4 | **4131.04** | 5986.00 | 14509.18 | 56.51 s |

可以看到：**同一条配置（B2）只把 n 从 3 改成 4，中位数就从 6262 跳到 4121**，
摆幅比任何两个配置之间的差异都大。原因是 64K prefill 的单次 TTFT 离散度极大
（P99 14.5 s vs 中位 4.1 s），而 n=3 时「中位数」就是 3 个样本里的第 2 个、
n=4 时是第 2、3 个的均值 —— 样本数一变，这个统计量本身就换了一个位置。
**所以 n=3 与 n=4 的两组数据都不能跨组比较**；能比的只有组内配对：

- n=3 组内：B2 6262 vs C4 6656 → 差 6%（在噪声内）
- n=4 组内：B2 4121 vs C6 4131 → 差 0.2%（持平）

两组配对都不支持「内核包让长序列 prefill 倒退 1.5–1.6×」。
同理，C4 当时只探到 conc 2，那个「最大并发 2」是**探测范围的上界**，不是实测失败点。

#### 结论：保留内核包（C4 为最终配置）

判据只剩一条证据链：在严格同口径的对比（ShareGPT，n=300）上，内核包
**+2.8% / +3.5%**；而 64K SLA 档位上 C4 与 C6 的通过并发相同，不存在它拖后腿的证据。
按「只在单档有效、其他档明显退化才不采纳」的验收标准，这条线倾向保留。

> **证据强度声明（如实标注）**：上述 C4 / C6 的消融数字来自**早期测量**，
> **其原始日志未随本次重跑一并归档**（见文末「日志归档范围声明」）。
> 因此「保留内核包」在当前提交包中属于**倾向性判断**，而非有原始日志兜底的结论 ——
> 它成立的依据是 +2.8% / +3.5% 两个 ShareGPT 读数均为正、且无一档退化。
> 评审若要求逐条日志对账，可把 **C6（不带内核包）视为等效配置**：
> 两者差异仅 2.8~3.5%，与测量噪声同量级，且 C6 少一组环境变量、复现更简单。

> **申报口径提示**：+2.8% 略低于我们自己设定的「>3% 才算有效」门槛，属于**边缘有效**，
> 价值主要在 conc 64 档（+3.5%）。本报告选择保留，理由是它在所有档位上都没有负向。
>
> 机理推测（**未做进一步验证，标注为推测**）：该 env 替换的 decode 路径是
> `fla/fused_recurrent.py` 与 `kernels/gdn_triton.py`（本模型 48 层线性注意力逐 token
> 都要走），收益随解码步数累积，因此在高并发长解码的 ShareGPT 档位上更明显。

## 第 5 段 · 结论与适用边界

### 5.1 结论

在 **2 × 海光 DCU BW150**、Qwen3.8-27B、SGLang 0.5.12 上，以本机自测的出厂默认基线
（B2，见第 2 段）为分母，最终配置取得：

| 指标 | 结果 |
|---|---|
| ShareGPT 输出吞吐 | **+43.7% ~ +152.5%**，5 个并发档全部提升，无退化档 |
| 官方 SLA 4K/1K 最大并发 | 16 → **32**（**+100%**） |
| 官方 SLA 64K/1K 最大并发 | 3 → **6**（**+100%**，两侧同口径 n=6；敏感度见 4.3） |
| 全档位测量方差 | 输出吞吐极差 **≤ 1.82%**（容差 ±5%） |

提升率的来源可以按贡献排序：**解开并发上限（3.1）> 保住 EAGLE 投机解码（3.2）>
prefill 批处理（3.4）> context-length 修复（3.3）> 内核包（3.5）**。
其中 3.2 是与官方基线拉开差距的机制性原因：第 2.4 节的交叉对照显示
官方 BW100 基线**没有启用投机解码**。

### 5.2 适用边界 —— 这套配置在什么情况下不成立（必读）

**① 长 prefill / 短解码的场景，我们没有优势。**
64K/1K 场景 conc 1 的 TTFT 是基线 6133.5 ms vs 本方案 6518.1 ms —— **我们略慢 6.3%**。
原因清楚：EAGLE 加速的是逐 token 解码，而 64K 场景的耗时几乎全在 prefill 上，
投机解码无从发力；`--chunked-prefill-size 32768` 反而让首 token 要等一整个 32K chunk。
**64K 档的 +100% 完全来自并发容量，不来自单请求速度。**
如果评测集的负载特征偏向「超长输入 + 极短输出」，本方案的收益会显著缩水。

**② TTFT 绝对值是退化的。**
ShareGPT conc 64 的 TTFT 中位：基线 219.1 ms → 本方案 390.5 ms（**+78%**）。
这是放大 prefill chunk 的直接代价。它以「TTFT 涨 171 ms」换来了
「SLA 4K 最大并发翻倍、吞吐 +44%」。**如果评判标准以单请求首字延迟为主，
这一项是负分** —— 我们选择这个交换，是因为赛题把 SLA 定义为
「TTFT < 5s 且 TPOT < 50ms」这类**门槛式**指标而非「越小越好」，
在门槛内有 10 倍以上余量时，换取吞吐与并发是划算的。

**③ 丢掉了前缀缓存（radix cache），这在重复前缀负载下会被放大。**
`--disable-radix-cache` 是解开并发上限的必要条件之一（3.1：框架下
`extra_buffer + disable_radix_cache` 直接 ValueError）。代价是**重复 prompt 必须重算 prefill**。
ShareGPT 是一组互不相同的对话，几乎测不出这项代价；
但**多轮对话、RAG、few-shot 同前缀**这类负载下，这项代价会成倍放大。
我们**测过**保留前缀缓存的那条路（B1：`extra_buffer` + 保留 radix + 24 并发）：
conc 1/16/64 = 27.07 / 286.07 / 302.49 tok/s，**每个档位都输给 B2 的 26.92 / 322.89 / 556.09**，
即便在 conc 16（B1 的 24 并发帽尚未触发）也输 12.9%。
所以在本实验覆盖的负载上，丢掉前缀缓存是划算的；**在重复前缀负载上结论可能反转，未验证**。

**④ 精度影响需要单独确认（见 5.3）。**
`--mamba-ssm-dtype bfloat16` 把 SSM 递推状态从 fp32 降到 bf16，而 SSM 状态是**跨序列递推**的，
误差会沿解码步累积；EAGLE 投机在本机（DCU 无树形采样 kernel）会降级为贪心验证，
与常规采样路径不同。这两项都改了数值，必须过精度门槛。

**⑤ 本结论只在「2 卡 TP=2」下成立。** 并发上限、KV 池容量、mamba 槽位、
`--mem-fraction-static 0.85` 的取舍都是按 2 张卡 65.5 GB × 2 的显存账本算出来的，
换卡数、换 TP/PP 切分都需要重测，不能直接外推。

### 5.3 精度校验

**口径**：`sglang.test.simple_eval_gsm8k`（框架自带，与官方同源），
5-shot、`temperature=0`（贪心）、`max_tokens=8192`、关闭思考模式
（`chat_template_kwargs.enable_thinking=False`）、全量 1314 题、32 线程。

**为什么必须显式关思考**：本模型 chat template 默认开启思考链
（`chat_template.jinja:46`：`if enable_thinking is undefined or enable_thinking is true`），
而 `ChatCompletionSampler` 默认 `max_tokens=2048` 会被思考链吃光、`content` 返回空串，
GSM8K 直接判 0 —— 那是口径错误，不是精度下降。这一点必须先排除。

| 配置 | GSM8K | 相对官方 97.0 | 相对本机基线 | 耗时 |
|---|---|---|---|---|
| 本机基线 B2 | **96.19%** | −0.81 pp | — | 477.4 s |
| **本方案** | **96.35%** | **−0.65 pp** | **+0.16 pp** | 364.6 s |

**结论：精度没有下降，反而略升（+0.16 pp，在 1314 题的统计噪声内属持平）。**

「基线跑出 96.19%，与官方公布的 97.0 只差 0.81 pp」这件事本身就是重要的旁证：
说明这条自建评测链路的口径与官方一致，因此它测出的「本方案没有下降」是可信的。
如果口径错了（比如没关思考模式），基线自己就会掉到接近 0，不可能对上 97.0。

**覆盖说明（如实标注）**：赛题的四项精度门槛中，本报告只完成了 **GSM8K**。
LiveCodeBench v6 / RealWorldQA / MathVision 的官方评测脚本在本镜像中不存在
（`lm_eval` / `lighteval` / `vlm_eval` / `evalplus` 全部 ModuleNotFoundError），
而赛题写明精度评测应「基于官方指定的数据版本、测试子集和评测脚本」。
**这三项的绝对值需要主办方提供官方评测脚本后补测。**

需要说明风险的是：本方案中**会改动数值**的改动只有两项 ——
`--mamba-ssm-dtype bfloat16`（SSM 递推状态 fp32→bf16）与 EAGLE 投机
（DCU 无树形采样 kernel，降级为贪心验证，`eagle_info.py:376`）。
其余（并发参数、chunk 参数、mem-fraction、`--disable-radix-cache`）都只影响调度与显存，不改数值。
GSM8K 覆盖了「长链推理 + 精确数值答案」这一类最容易被数值扰动击穿的任务，
它没掉，是这三项风险的主要证据；但 LiveCodeBench（代码生成）
与 MathVision（多模态数值）确实各有独立的失败模式，**未测就是未测，不声称**。

### 5.4 未吃到的收益（后续可挖掘，本轮不计入成绩）

1. **64K 档的探测上界是 conc 6**：本方案 conc 6 通过（TTFT 15,508 ms，余量 22%）。
   继续上探 conc 7/8 时，门槛预计会先被 TTFT 击穿（conc 6 已到 15.5 s / 20 s），
   故 64K 最大并发只申报到 6。更深的并发容量需要配合更大的 prefill 批预算，
   而那会改动 KV 池与激活显存的分配、需重跑全部档位与精度校验，**本轮未做**。
2. **draft-extend 的 CUDA graph 在 fa3 上被跳过**：启动日志明确打印
   `Skip draft extend cuda graph capture because the attention backend is not supported yet: FlashAttentionBackend`。
   这是一块现成但拿不到的收益（需要 attention backend 侧支持，属框架改动，超出本轮范围）。
3. **`SGLANG_ENABLE_OVERLAP_PLAN_STREAM` 与 fa3 互斥**（3.7 已记录崩溃堆栈），
   而 HCU 白名单下本模型只能用 fa3 —— 这条路要解开必须先有支持该接口的 attention backend。
